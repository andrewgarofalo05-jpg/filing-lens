# Learn and own the project in 3–5 hours a week

The objective is to explain and improve the work yourself, not to memorize generated code.
Track what you understand and what you verified in a short learning journal.

| Week | Focus | Small deliverable |
| --- | --- | --- |
| 1 | Run the demo and tests; read models.py | Explain accession, CIK and reporting dates |
| 2 | Read financials.py and its tests | Calculate revenue change by hand and match the app |
| 3 | Trace a real filing through sec.py | Draw where data is fetched, cached and displayed |
| 4 | Read filings.py | Add two synthetic retrieval cases and explain misses |
| 5 | Read local_ai.py | Explain retrieval vs generation and cite one failure mode |
| 6 | Review security and data methodology | Demonstrate a missing-value or conflict rejection |
| 7 | Improve one small interface detail | Submit a focused, tested local change |
| 8 | Expand evidence evaluation | Add 3–5 legally shareable, attributed test cases |
| 9 | Compare one more company's annual periods | Document unsupported concepts or ambiguity |
| 10 | Audit a local AI draft, if hardware permits | Record unsupported claims instead of hiding them |
| 11 | Rehearse the two-minute demo | Explain decisions without reading the README |
| 12 | Review release and résumé wording | Publish only what you can demonstrate and defend |

Suggested weekly split: one hour learning, one hour experimenting, one hour testing/documenting;
use optional extra time for a small improvement. Do not begin with model training or a vector DB.

## Honest résumé language

Use only after you can explain, run and maintain the project:

“Built and tested a Python/Streamlit SEC filing research assistant with source-linked retrieval,
deterministic annual financial comparisons, and an optional local-LLM explanation layer.”

Add the actual test/evaluation count only when it remains current. Do not claim production users,
investment returns, research accuracy, model training or GitHub stars without evidence. A public
repository, a clear demo and a thoughtful discussion of failure modes are useful without stars.
Be transparent in interviews about AI-assisted development and which improvements you made.
